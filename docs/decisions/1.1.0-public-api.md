# `voice-runtime` 1.1.0 public API decision

Status: locked; the Team 1 implementation is materialized in the current
worktree. This file is the tracked decision copy. The Team 1 plan may add
detail, but implementation must not contradict these decisions. External
service, live-provider, protected-branch, and post-publish evidence remain
release gates.

## Package boundary

- Package name: `voice-runtime`.
- Runtime: server-side Node.js only for 1.1.0. Browser code connects to the
  Node transport boundary and does not import the package directly.
- Module formats: ESM and CommonJS.
- Advanced APIs: exported from the package root. No feature-specific subpaths.
- Supported Node lines: `^22.0.0 || ^24.0.0 || ^26.0.0`. Node 20, odd lines,
  and future untested lines are outside the support claim.
- Stable built-in transports for this release: browser Web Client Audio and
  inbound Twilio Media Streams. Other provider capabilities retain their
  existing maturity labels until their evidence gate passes.

## Managed entry point

The primary beginner API is `createVoiceAgent({ prompt, providers, ... })`.
Provider selection remains independent for telephony, STT, LLM, and TTS. A
caller may use built-in adapters or supply custom provider implementations.
Explicit credentials take precedence over documented environment variables.
The SDK validates configuration and capabilities before a live session starts.

`VoiceAgentRunOptions.signal` is the caller's startup and run cancellation
signal. `VoiceAgentRunOptions.startupTimeoutMs` is an optional positive integer
with a default of `10_000`; it bounds runtime startup and a call-handle
factory's caller-visible startup. A custom `VoiceAgentCallHandleFactory`
receives `{ sessionId, call, channel, signal }`, where `call` is the immutable
validated `CallSnapshot` and `signal` is the combined signal for caller abort,
agent shutdown, and the startup deadline. A factory that ignores the signal
does not delay `agent.start()` past the deadline. Its late handle is validated
and closed exactly once, and cannot attach to a session. A signal that is
already aborted rejects before provider work; a later abort prevents
attachment and runs the same bounded cleanup path. These rules apply to the
runtime-start Promise as well, and an ignored runtime signal is reported as
degraded shutdown rather than treated as a successful start.

The host application owns authentication, authorization, endpoint creation,
provider secrets, domain tools, business workflows, and durable business state.
TVIC does not infer permission from a prompt and does not create outbound calls
in this release.

## Session and event protocol

`agent.start()` returns `Promise<VoiceAgentSession>`. The resolved session has a
`sessionId` and a `run` result that is both awaitable and asynchronously
iterable. The normal beginner flow is:

```ts
const session = await agent.start({ call, callHandle });
for await (const event of session.run) {
  console.log(event);
}
```

`run` is deferred until its first Promise or iterator observation. Exactly one
protocol is claimed. Promise-first observation is result-only and does not
retain public event history. Iterator-first observation yields the bounded raw
event history, including `call_ended`, and waits for managed finalization before
returning `done: true`. A second protocol claim fails with
`voice_runtime.events_already_consumed`. `agent.run()` is the result-only
convenience path.

The protocol claim is exclusive for event ownership, not for reading the same
settlement. The exact matrix is: Promise-first followed by iteration rejects;
iterator-first followed by `await run`, `run.then(...)`, or
`Promise.resolve(run)` delegates to the already-claimed public completion and
is allowed; a second iterator always rejects. Internal runtime bookkeeping
never performs those Promise observations on the public thenable.

The managed facade uses one runtime lifecycle and finalization path. It does
not create a second provider pipeline or infer terminal state from consumer
timing. Queue capacity, cancellation, terminal signal arbitration, cleanup
precedence, and late-event fencing are implementation requirements in the Team
1 plan and Team 2 handoff.

## Call and transport boundary

The managed boundary validates the complete `Call` discriminated union before
creating a session or accepting a call handle. It checks the required fields
for every status, timestamps, normalized audio format, and nested normalized
errors. It hands downstream code a frozen `CallSnapshot` containing only the
known validated fields. Unknown extension fields are allowed after known fields
pass. Hostile getters are never invoked; descriptor-related Proxy traps may
run while inspecting an arbitrary object, and a throwing trap fails with
`voice_runtime.invalid_call` without invoking a factory or closing a
caller-owned handle. In a failed call snapshot, the normalized error keeps its
known scalar fields and sanitized metadata but omits arbitrary `error.cause`;
cycles, getters, and provider secrets in a cause never cross this boundary.

`CallHandle` remains the transport boundary. The host provides an authenticated
browser or phone connection and the handle exposes the provider event stream,
send/control operations, and close behavior. A factory result transfers handle
ownership to TVIC only after the full handle shape and call ID match pass.

The low-level `PipelineVoiceLoopResult` includes both `terminalReason` and
`terminalSource`. `terminalReason` is one of `completed`, `cancelled`,
`remote_hangup`, or `failed`; `terminalSource` records the winning live signal
such as `caller_abort`, `remote_transport`, `run_timeout`, or
`provider_runtime`. The managed facade derives close and durable finalization
from that source instead of inspecting an abort flag after the fact.

## Durable store ownership

`RuntimeOptions.durableStoreOwnership` is `"runtime" | "caller"`.
The default is `"runtime"`, including for the runtime-created in-memory
store. A caller that injects a shared durable store must choose `"caller"`.
Runtime-owned stores close exactly once after a successful runtime start and
stop. Caller-owned stores are detached but never closed by TVIC. Stop before a
successful runtime start has no store-close obligation in either mode. A public
shutdown timeout does not make a caller-owned store safe to close; the caller
waits for the health snapshot to report that late cleanup is complete.
The internal durable `EndSessionRequest` also carries an optional
`terminalSource` provenance field. Managed paths always provide one of
`normal_completion`, `operator_stop`, `caller_abort`, `run_timeout`,
`remote_transport`, or `provider_runtime`. Runtime recovery and shutdown
finalization paths use `runtime_recovery` and `runtime_shutdown`, respectively.
Low-level callers from the existing runtime contract may omit the field for
compatibility; normalization maps
`completed` to `normal_completion`, `timeout` to `run_timeout`,
`caller_hangup` to `caller_abort`, `transport_lost` to `remote_transport`,
`operator_requested` to `operator_stop`, `recovery_expired` to
`runtime_recovery`, and `shutdown` to `runtime_shutdown`. An omitted `failed`
or otherwise unclassifiable request becomes `legacy_unknown`. These additional
compatibility values are `runtime_recovery`, `runtime_shutdown`, and
`legacy_unknown`. This does not add a public cancellation reason; it prevents
finalization from reconstructing the source from an aborted signal or cleanup
timing. `runtime_restarted` remains a turn-recovery reason, not a session
terminal source.
Persisted terminal sessions also carry `terminalSource` in schema version 2.
The persisted type adds the compatibility-only value `legacy_unknown`; new
runs never emit it. A schema version 1 session migrates `completed` to
`normal_completion`, while both `failed` and `cancelled` become
`legacy_unknown`. An old failed record cannot distinguish provider failure from
timeout, and an old cancellation record cannot prove whether the caller,
operator, or remote transport won. The migration is explicit and idempotent,
and an unknown legacy source never selects a new retry or recovery branch.

## Error and compatibility boundary

Errors use lowercase namespaced codes and the canonical normalized TVIC shape.
The 1.1.0 migration keeps registered legacy codes in bounded sanitized
metadata, maps them to canonical codes, and never uses unknown persisted codes
to select retry behavior. Persisted reads return a separate compatibility
envelope with `error`, `knownCode`, and `migratedAlias` fields.

The host controls logs and custom-provider state. TVIC redaction applies only
to TVIC-owned events, error metadata, persisted compatibility envelopes, and
the internal provider secret context.

## Explicit non-goals

- No direct browser import of `voice-runtime`.
- No outbound telephony creation.
- No hidden provider fallback or model routing.
- No recordings, transcript retention, dashboards, or business-workflow APIs.
- No claim that TVIC can control custom-provider code or host-owned logs.

Any change to these decisions requires updating this file, the Team 1 plan,
the public examples, and the release evidence before implementation is called
complete.
