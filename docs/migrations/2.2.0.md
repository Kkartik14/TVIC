# Upgrade to `voice-runtime` 2.2.0

Version 2.2.0 adds provider-aware speech controls and capability preflight. It
also tightens several TTS validation rules and adds compatibility issue codes.
These notes describe behavior changes to review when upgrading from 2.1.0.
Read the compatibility changes below before upgrading: several configurations
or exhaustive consumers accepted in 2.1.0 may need changes.

## Compatibility changes to check first

- **A session can have only one active turn in every runtime configuration.**
  A second `startTurn()` rejects with `turn.already_active`, whether the runtime
  uses its default in-memory store, deprecated per-store options, or a
  `durableStore`. If a stopped runtime leaves a turn in `started`, call
  `endTurn()` or attach the session to a runtime with `attachSession()` so it
  can recover the turn.
- **TTS failover metadata must be structured-cloneable.** Metadata is copied
  before the primary provider is called, even when synthesis succeeds. Class
  instances become plain objects and lose methods and custom prototypes; use
  plain records, arrays, and primitive values.
- **Configured failover speed must be supported by both child providers.**
  Remove the speed setting or use providers with compatible declared ranges.
- **`ProviderCompatibilityIssueCode` has new members.** Update exhaustive
  switches for `tts.selection_unsupported`, `turn_profile.unsupported`,
  `tts_text_control.unsupported`, and `tts_speed.unsupported`.

## STT vocabulary

Through 2.1.0, every call sent each tool's `name` to the STT provider as
vocabulary. In 2.2.0, tool names are excluded by default. Set
`includeToolNamesInSttVocabulary: true` to opt in; prefer `sttVocabulary`
with words callers actually say. The 256-term input limit applies before
trimming and de-duplication. A managed call can opt in with
`await agent.start({ callHandle, includeToolNamesInSttVocabulary: true })`.

Vocabulary is checked against the selected model:

- Deepgram accepts vocabulary only on Nova-2 and Nova-3 models, with at most
  100 terms.
- Sarvam accepts it only on `saaras:v4`, with at most 50 terms of up to 64
  characters.
- Set `allowUnknownModel: true` on either provider, or on an individual open
  request, to forward vocabulary to an unlisted model. Term validation and
  limits still apply; confirm support with that provider before relying on the
  model. Without this opt-in, unsupported combinations fail before the stream
  opens with `stt.vocabulary_unsupported`.

Deepgram, Cartesia, ElevenLabs, AssemblyAI, and Sarvam send vocabulary in the
WebSocket URL, where it can appear in URL logs. Never include credentials,
personal data, or other secrets in vocabulary terms. Soniox uses the WebSocket
context payload instead.

## Soniox authentication and language hints

Soniox authentication is sent in the WebSocket `Authorization` header. If a
proxy or WebSocket gateway filters headers, allow this header through.
`best_effort` Soniox language hints are now non-restrictive:
`language_hints_strict` is sent as `false`. Use a fixed-language policy when
the provider must restrict recognition to the supplied language.

## STT reconnect buffering

The default PCM16 16 kHz mono reconnect journal now holds up to 1,600,640 bytes
and 5,018 commands per stream, up from 320,000 bytes and 512 commands. Derived
limits clamp at 16 MiB and 8,192 commands instead of rejecting an otherwise
valid stream. Overflow errors report the limiting unit, configured cap, and
observed size.

In 2.1.0, every call with STT reconnect enabled ended after about 10 seconds,
even when the provider had no fault. The new journal lets a stream survive an
outage for about 4–5 seconds with 5 ms frames that omit their duration, about
20 seconds with declared 5 ms frames, and about 25 seconds nominally with frames
of 10 ms or more; the last limit is a timer tie. The default retained payload is
up to 1,600,640 bytes and 5,018 commands. Retained audio uses roughly twice its
payload size on the heap. Hosts that emit short chunks should coalesce them or
set `maxBufferedCommands`; `maxBufferedBytes` and `maxBufferedCommands` can also
be set explicitly to fit the process memory budget. Derived defaults clamp at
16 MiB and 8,192 commands rather than rejecting an otherwise valid stream.

## TTS failover

### Request mapping with `fallbackRequestVariants`

`fallbackRequestVariants` is the option for declaring how a primary call maps to
the fallback provider. Each variant has a `when` selector, which matches the
primary call's effective model, voice, language, or speed, and a `fallback`
selection with the model, voice, or language to send:

```ts
createTtsFailoverProvider({
  primary,
  fallback,
  fallbackRequestVariants: [
    {
      when: { model: "bulbul:v3", voice: "shubh" },
      fallback: { model: "eleven_flash_v2_5", voice: "fallback-voice-id" },
    },
  ],
});
```

- An omitted `when` field matches any value.
- An omitted fallback field uses the fallback provider's configured default.
  It does not inherit the primary request's value, so set `fallback.model`
  explicitly when the fallback should use a specific model.
- Without `mapFallbackRequest`, the matching variant maps the fallback request
  itself. A call that matches no variant fails before the primary is called. A
  call that matches several variants with different fallback targets also fails
  before the primary is called; add a mapper to choose.
- With `mapFallbackRequest`, variants declare the mapper's allowed output so
  both providers can be preflighted at call time. The mapped request must match
  one variant.
- A `mapFallbackRequest` configuration without variants remains valid. Its
  mapped request is validated only when failover is dispatched.

If you maintain a configuration that used a separate voice mapping table, move
each entry to a variant: put the requested model and voice in `when`, and the
mapped model and voice in `fallback`.

When a managed agent enforces capability snapshots and the fallback uses
account-backed voices, declare `fallbackRequestVariants` so startup can
validate the fallback voice before a call. For dialogue adapters behind
failover, declare a variant for every registered primary dialogue voice and map
only to voices registered by the fallback dialogue adapter. The snapshot loader
receives provider/model/voice selections for both children and for each
declared variant. Startup checks both sides even when both children use the
same vendor account. A direct `synthesize()` call that passes capability
snapshots to such a failover provider without variants fails with
`provider.invalid_request` before the primary is called.

### Request metadata and errors

Failover copies request metadata before calling the primary, so metadata must be
structured-cloneable on every request. Class instances become plain objects;
methods and custom prototypes are not retained. Use plain records, arrays, and
primitive values for metadata. The failover mapper may return a fresh object, but
it must preserve session and turn IDs, text, format, timing options, controls,
metadata, usage reporting, and the caller's `signal`. Validation errors list
protected fields that were changed or dropped.

If failover cannot be attempted because the mapped fallback request fails
validation, the mapper throws, or `shouldFallback` throws, TVIC throws the
primary provider's error with its code and retryability unchanged. The error
adds `metadata.fallbackValidationFailure`, which carries the failure's `code`,
`category`, `message`, and, when known, `provider`. Provider and
cancellation errors keep their code, retryability, and existing cause.
Non-cancellation errors returned from an attempted fallback include
`metadata.primaryProvider` and `metadata.primaryCode`; a primary provider error
that does not trigger fallback is propagated unchanged and may not carry that
metadata.

Failover now reports the primary provider's model and voice catalogs when a
request mapper owns selection. Text controls are checked against the primary
before synthesis and against the fallback only if failover is attempted. This
differs from speed preflight when no request mapper is configured: speed is
checked against both children before primary synthesis, while unsupported
fallback text controls can prevent fallback only after the primary fails.

### Speed

When speed is configured, both children must declare a compatible speed range.
Remove speed or choose providers with overlapping declared ranges if failover
construction rejects the configuration.

## Cartesia settings

- Speed must be between `0.6` and `1.5`, inclusive. A per-call speed also needs
  a current capability fact proving the selected voice is not a Professional
  Voice Clone. A speed configured on the adapter is checked only when snapshots
  are supplied.
- Normalization and pronunciation dictionary IDs are accepted only for models
  where the catalog declares support, currently Sonic 3.6 models.
- Explicit languages are checked against the chosen model when a language map is
  published. For catalog models without a map, valid language tags pass through
  to Cartesia without local language support validation.
- `finish()` rethrows a provider failure already received by the stream. Catch
  failures from `finish()` and stop using that stream.

Voice facts come from capability snapshots. The adapter option
`capabilitySnapshot` takes a snapshot from `loadCartesiaCapabilitySnapshot()` or
one built with `createProviderCapabilitySnapshot()`. A stale snapshot is treated
as absent, so configured voices keep working.

Cartesia passes provider markup embedded in transcript text through by default,
preserving 2.1 behavior for hosts whose generated transcript intentionally uses
Cartesia tags such as `<emotion>` or `[laughter]`. A live call confirmed that
`<spell>...</spell>` is interpreted as an instruction and entity escapes are
spoken as their entity names. Set `transcriptMarkup: "reject"` to reject
supported provider markup in source text. Typed `textControls` remain available
for spelling and pauses. TVIC leaves source ampersands and angle characters
unchanged in either mode.

## ElevenLabs settings

The adapter rejects `language` for Text-to-Dialogue models and for
`eleven_multilingual_v2`, where the configured `language_code` option is not
supported by this API route. Earlier behavior omitted the language and reported
it as supported. Omit the language or choose a model and route that accepts it.

SSML parsing is off by default on regular WebSocket routes. Setting
`enableSsmlParsing: true` is an accepted opt-in that sends
`enable_ssml_parsing=true`. Text is still passed through exactly, with no
escaping, and the provider may interpret tag-shaped text on supported routes.

The HTTP and HTTP-streaming routes have no SSML setting: a live check on
2026-10-28 found they interpret tags such as `<break>` on non-v3 models and
ignore `enable_ssml_parsing`. On those routes `enableSsmlParsing: true` is
accepted and sends nothing, and `enableSsmlParsing: false` is rejected because
it cannot be honored. The same check found that a `<phoneme>` tag can drop the
wrapped word, so test phoneme markup with the selected model before relying on
it.

Voice categories in capability snapshots now include `famous` and
`high_quality`. Null locale entries no longer erase other valid verified
locales for the same voice and model. A model-specific voice check now requires
a fact for that model. Hand-built snapshots that only record a model-independent
voice fact must add a model-scoped availability fact for each selected model.
The ElevenLabs loader now emits those facts for requested model IDs.

HTTP Text-to-Dialogue defaults to `eleven_v3` when the configured speech model
is not a dialogue model. Explicit dialogue models must start with `eleven_v3`.
For a managed WebSocket dialogue agent, every `dialogueVoices` entry is checked
before call startup and is included in the snapshot loader context.

### Model, language, speed, and custom URL rules

ElevenLabs v3 and v4 dialogue requests use supported Text-to-Dialogue routes. If a
dialogue request omits model, the adapter uses its configured model when that
model is a dialogue model; otherwise it uses `eleven_v3`. v4 Turbo remains
WebSocket-only, and multi-context dialogue supports v3 models.

BCP-47 TTS language tags are mapped to the provider's language code.
Flash/Turbo routes reject unsupported languages, and v3/v4 dialogue routes
reject speed settings. For regular TTS custom URLs, include the literal
`:voice_id` placeholder when using per-call voice overrides so the selected
voice can be inserted into the route.

## Sarvam Bulbul v4 Flash temperature

An explicit `temperature` is now accepted and sent for `bulbul:v4-flash` on the
WebSocket route, as it already was on REST and HTTP streaming. TVIC sends no
default temperature for v4 on any route. A live check on 2026-10-28 found that
all three routes accept values from 0.01 to 1 and reject values outside that
range with the same error. The [WebSocket reference](https://docs.sarvam.ai/api-reference/text-to-speech/stream)
and [REST reference](https://docs.sarvam.ai/api-reference/text-to-speech/convert)
list v4 Flash as supported, while the [v4 best-practices guide](https://docs.sarvam.ai/api/api-guides-tutorials/text-to-speech/best-practices)
says temperature is silently ignored and the [HTTP-stream guide](https://docs.sarvam.ai/api/api-guides-tutorials/text-to-speech/streaming-api/http-stream)
limits it to v3. The live check could not confirm an audible effect on v4, so
treat v4 temperature as unverified tuning.

## Snapshot loader and call-start deadlines

`loadProviderCapabilitySnapshots` must return an array. Its deadline is now
separate from `startupTimeoutMs`: snapshot loading defaults to 30 seconds, and
ordinary startup and the call-handle factory keep the 10-second default.
`providerCapabilitySnapshotTimeoutMs` can shorten or extend only the loader
budget. The loader selection now includes
`providerCapabilitySnapshotProviders`,
`providerCapabilitySnapshotSelections`, and
`providerCapabilitySnapshotVoices` as provider/model/voice selections;
selections may identify request-selected versus mapping-selected models with
`modelSource`. Callbacks may use these fields to fetch all snapshots the
selected adapter needs. The bundled Cartesia loader returns one
snapshot, so wrap it in an array from the callback. Snapshot-load timeouts
retain `voice_runtime.start_timeout` and carry
`metadata.timeoutScope: "provider_capability_snapshot_loader"` with a
loader-specific message.

## Provider compatibility issue codes

`ProviderCompatibilityIssueCode` now includes:

- `tts.selection_unsupported`
- `turn_profile.unsupported`
- `tts_text_control.unsupported`
- `tts_speed.unsupported`

Update exhaustive switches over compatibility issue codes to handle these
values.

## Provider error and selection results

Managed speech-selection validation is reported as
`voice_runtime.invalid_config`; `metadata.selectionErrorCode` contains the
underlying selection issue. Unsupported language selection uses
`tts.language_unsupported`. Cartesia and ElevenLabs voice-not-found responses
use `provider.voice_unsupported` across their routes. Update error handling
that matches provider codes or selection metadata.

The OpenAI Responses adapter reports malformed accumulated tool arguments in
`response.completed` as a non-retriable `llm.failed` event. Do not retry that
failure as though the stream ended transiently.

AssemblyAI Universal-3 Pro context-update failures use
`stt.context_update_failed` and do not end the call. The error's `retriable`
flag reflects the underlying failure. An ambiguous timeout or cancellation on
a live stream can trigger reconnect to fence a late provider write; caller
audio replay continues while TVIC restores the latest accepted context. The
context-update deadline defaults to 2 seconds and can be set with
`contextUpdateTimeoutMs` on `withSttReconnect()`.

## Output sequences and Sarvam Odia

Sarvam WebSocket and ElevenLabs dialogue output sequence numbers restart at 1
after each commit. Consumers that deduplicate output across commits must include
the commit boundary in their deduplication key; a sequence number alone can
repeat within one turn.

Sarvam Odia is reported in TVIC properties and capabilities as `or-IN`, while
the provider wire value remains `od-IN`. Existing `od-IN` input remains a
compatible alias.

## Cartesia charactersSent

`charactersSent` counts the serialized transcript at each provider write
attempt, including generated control markup. Buffered text is counted only
when emitted. The count describes adapter attempts and can include text from an
operation that fails before provider acceptance; do not treat it as an
acknowledged billing or delivery total.

## Durable sessions and turns

The default `criticalWriteTimeoutMs` is now 2,000 ms. Review any explicit
durable-policy override against the latency of the configured store. Most
durable-write failures now end the call cleanly instead of leaving it connected
but unable to process caller input. If `CallHandle.close()` times out, the event
uses `voice_runtime.call_close_timeout`; a plain `Error` rejection uses
`voice_runtime.call_close_failed`, while an existing TVIC-coded error keeps its
code. This change requires no database schema migration.

A session has at most one active turn. A turn is active from `startTurn` until
it reaches a terminal state (completed, failed, or cancelled). This applies to
default in-memory, deprecated per-store, and `durableStore` configurations.
`startTurn` rejects with `turn.already_active` while the session's current turn
is active; call `endTurn()` or attach the session with `attachSession()` to
recover a turn left `started` by a stopped runtime. `session.state.currentTurnId`
is the ID of the active turn and is absent when no turn is active. Session end
and attachment recovery close any active turn and clear `currentTurnId`.

Custom `durableStore` adapters must serialize `runSessionTransaction()` and
`runUnfencedSessionTransaction()` per session, or reject a stale snapshot with
`RecordConflictError` without committing any callback writes. This preserves
atomic session, turn, tool, and outbox updates under concurrent requests.

`sessionStore`, `turnStore`, and `toolCallStore` are deprecated
compatibility options for a single process. The runtime wraps them in an
in-memory durable facade: leases, the outbox, and per-session write ordering
stay in process memory, so this configuration is not safe across processes or
restarts.

Lifecycle writes that touch several records are not atomic for these stores. If
a later write fails, the operation rejects and the runtime tries to restore
earlier writes. A store implementing only the public `SessionStore`,
`TurnStore`, or `ToolCallStore` interface can retain records written before
the failure. Session end and recovery still close any turn left active. For
atomic multi-record writes, pass a `durableStore` whose
`runSessionTransaction` commits or rolls back the operation's writes together.
If rollback leaves a started turn active, another `startTurn()` can reject with
`turn.already_active` until session end or attachment recovery closes that turn.
The separate store options remain available through 2.x and are planned for
removal in 3.0.0.

## Twilio and STT terminal reasons

Malformed Twilio start, stop, or DTMF protocol messages fail with a protocol
reason and are no longer reported to the host as caller hangups. Chunk gaps and
timestamp progression anomalies are counted and tolerated; exact duplicate
and outbound media frames are dropped and counted.

Unexpected STT end-of-stream is reported as
`call_ended.reason = failed`, not `remote_hangup`. Update consumers that
treated every STT EOF as a caller hangup. On Soniox, final transcript text
received after end-of-audio can now be emitted when the provider closes without
its finished marker.

Text-only delivery that settles after hangup, cancellation, or STT shutdown no
longer completes the turn or writes it to memory. The runtime skips delivery
when terminal shutdown is already observed. A true `delivery.text` transport
receipt remains `transport_accepted`.

## Managed event iteration

`session.run` remains both the run result and its single-consumer event
stream. Awaiting `session.run` or `finalSession` is the authoritative
completion signal. If a `for await` loop exits because the stream ends, the
consumer breaks or throws, or the stream fails, managed finalization (session
end and call close) now finishes or reaches its shutdown deadline before the
loop exits. If the run rejects, the loop throws the same error as
`await session.run`. Breaking out of the loop cancels the session. Handle
rejections from both the loop and the awaited `session.run`.
