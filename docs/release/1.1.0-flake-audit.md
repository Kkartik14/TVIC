# 1.1.0 flake audit

Status: in progress

This audit records synchronization choices for timing-sensitive tests. It does
not treat a retry as proof of correctness. A test is considered stable only when
it waits for the state transition it is asserting and cleans up the resources it
created.

| Test surface                                      | Synchronization used                                                                            | Local repeat and result                                                               | CI placement                                          | Remaining limitation                                                           |
| ------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------ |
| `packages/runtime/test/dual-protocol.test.ts`     | The event queue completion and the result promise are both awaited; no arbitrary sleep is used. | `pnpm dual-protocol:stress` ran 1,000 iterations and passed.                          | PR runtime, main runtime matrix, release verification | Provider latency is represented by deterministic fixtures, not a paid service. |
| `packages/runtime/test/recovery-timing.test.ts`   | Controlled clock and explicit deadline completion.                                              | Included in the repository test suite; no intermittent failure observed in this pass. | PR runtime and release verification                   | A future change to timer ownership must preserve the injected clock.           |
| `packages/runtime/test/durable-race.test.ts`      | Store barriers and lease state transitions.                                                     | Included in the repository test suite; durable service runs are required for release. | Durable PR scope, main durable, release verification  | Local process tests do not prove cross-region database behavior.               |
| `packages/runtime/test/chaos.test.ts`             | Named failure stages and explicit cleanup assertions.                                           | Included in the repository test suite; no intermittent failure observed in this pass. | PR runtime and release verification                   | Fault cases remain simulated at provider boundaries.                           |
| `examples/live-call/test/ingress.test.ts`         | Real local HTTP and WebSocket close events are awaited.                                         | 13 tests passed, including concurrent duplicate TwiML delivery.                       | Security job and release security                     | The test uses an in-memory replay store for deterministic handler coverage.    |
| `examples/live-call/test/replay-redis.test.ts`    | Redis Lua reservation and completion are awaited across two clients.                            | 2 tests passed against the local Redis service on 2026-09-15.                         | Release verification with `REDIS_URL`                 | A real multi-process deployment still needs operational Redis monitoring.      |
| `packages/providers/test/twilio-webhooks.test.ts` | Pure signature calculations, no wall-clock dependency.                                          | 23 tests passed.                                                                      | Security job and provider suite                       | Twilio's own delivery behavior is outside the unit fixture.                    |
| `examples/voice-mode/test/*`                      | Protocol barriers and socket lifecycle events.                                                  | Included in the repository test suite; no intermittent failure observed in this pass. | PR runtime and main runtime                           | Browser scheduling is not reproduced by Node tests.                            |

There is no quarantine list for this release. If a P0 or P1 intermittent failure
appears, record the failing command, first and last failing commit, owner, issue,
and expiry date here before changing the CI retry policy.
